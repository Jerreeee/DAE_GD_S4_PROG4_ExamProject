# Asset System Rework — Design Rationale & Thought Process

## Why This Rework?

Two problems drove this:

1. **Unstable handles**: `AssetHandle` (UUID) was generated by an incrementing counter. The same asset got a different handle every run. This makes any kind of serialized asset manifest impossible — you can't store `handle = 42` in a file and expect it to mean the same asset next launch.

2. **No real Runtime vs Editor separation**: `RuntimeResourceManager` existed as an empty stub. `EditorResourceManager` was doing everything — registration, loading, caching — with no distinction between "editor-time setup" and "runtime serving". In a real engine these are completely different systems.

The goal: **mirror how professional game engines handle asset management**, within the constraints of the project (no editor, no binary asset compilation, loose source files on disk).

---

## How Real Engines Do It

### The Key Insight

In a shipped game, **source files don't exist at runtime**. A `.png` is compiled into a GPU-ready binary format. A `.wav` is compiled into a platform-specific audio buffer. All of this compiled data is packed into an **AssetBundle** (Unity) or **uasset/pak** (Unreal).

The runtime asset manager:
1. Reads a bundle/pack file
2. Deserializes pre-compiled asset data directly into engine objects
3. Resolves cross-asset references (e.g. a Material referencing a Texture) using stable UUIDs/GUIDs that were baked in at build time

### Dependencies

Assets reference other assets by UUID. The bundle header (manifest) lists which assets depend on which. When you load a level, the engine:
- Looks at what the level asset depends on
- Loads those dependencies first (depth-first)
- Then loads the level itself
- All cross-asset references resolve via the UUID-to-loaded-object registry

### What We Can Mimic

We don't have:
- An editor
- Asset compilation
- Binary blob packs

We do have:
- Source files on disk (PNG, CSV, OTF, WAV)
- The same **logical** flow

So our "AssetBundle" is a **manifest file** that contains the same metadata a real bundle header would have: UUIDs, asset types, file paths, dependencies. The RuntimeResourceManager reads this manifest and loads loose files instead of binary blobs. The interface and logic are identical — only the backing store differs.

## Design Decisions

### 1. Hash-Based UUIDs (FNV-1a 64-bit)

**Problem:** Incrementing counter gives different handles each run. Can't serialize handles to disk.

**Solution:** Hash the asset's virtual path using FNV-1a 64-bit.

```
"Textures/bub.png" → 0xA3F2B1C4D5E6F789  (always the same)
"Fonts/Pixel_NES.otf/@20" → 0x12AB34CD56EF7890  (always the same)
```

Why FNV-1a:
- Zero dependencies (10 lines of pure C++20)
- `constexpr` — can be evaluated at compile time
- Good avalanche for short path strings
- 64-bit: birthday-problem collision at 50% probability ≈ 4 billion assets (BubbleBobble has ~50)

Font variants use `uniqueID` (e.g. `@20` for 20pt). The virtual path is `filepath / uniqueID`, so each font size gets its own stable handle.

**Important:** Virtual paths must always use `generic_string()` (forward slashes) as the hash input, never `native()`. This ensures cross-platform consistency.

**Session-unique handles:** `ResourceManager::AddAsset()` (for runtime-created assets like Sprites) still needs unique-but-not-stable handles. These use a counter with a high-bit sentinel (`0xFFFF000000000000 | ++counter`) to avoid colliding with path hashes.

### 2. Relative Paths in AssetMetadata

**Problem:** Importers currently call `AssetImporter::GetFullDatapath(relativePath)` in their constructors, storing absolute paths in `AssetMetadata::filepath`. The hash of the absolute path includes the machine's data directory location — different machines give different hashes.

**Solution:** Importers store **relative** paths in metadata. The absolute path is reconstructed at load time:
```cpp
// In ImportAsset static method:
auto fullPath = AssetImporter::GetInstance().GetFullDatapath(metadata.filepath);
```

This means `filepath` in the manifest is a portable relative path like `"Textures/bub.png"`, not `"C:/GD/.../Data/Textures/bub.png"`.

### 3. Centralized AssetManifest

**Problem:** Asset registration was scattered across scene builders. Every builder called `ImportAsset()` with its own importers. No single place listed what assets the game needed. This was fine for lazy loading but incompatible with a pre-built manifest.

**Solution:** `BubbleBobble::AssetManifest::RegisterAll()` — a single static method that registers every game asset. This is the equivalent of a "project file" in Unity/Unreal. In a real engine this file is generated by the editor. Here it's hand-written C++.

### 4. Explicit Dependency Declaration

**Problem:** `TileMapImporter::ImportAsset` was calling `AssetImporter::ImportAsset(TextureImporter(...))` recursively inside its own import. This created hidden dependencies and was fragile with threading.

**Solution:** Dependencies are declared explicitly in `AssetManifest::RegisterAll()` via a `.DependsOn(handle)` fluent API:

```cpp
auto tex1 = ai.ImportAsset(TextureImporter("Levels/1/Big.png"));
ai.ImportAsset(TileMapImporter("Levels/1/TileMapData.txt").DependsOn(tex1));
```

This mirrors how real engines track dependencies in bundle headers. The RuntimeResourceManager then loads all declared dependencies before loading the dependent asset.

Why explicit over auto-detected:
- Auto-detection requires parsing files just to enumerate deps (expensive, complex)
- Real engines have the editor track deps as you author assets — explicit declaration is the hand-coded equivalent
- Explicit deps are self-documenting in the manifest

### 5. Manifest Format: Human-Readable Text

Simple text file, no external libraries. Starting with text (not binary) because:
- Opens in any text editor — immediately readable when debugging
- Easy to verify `RegisterAll()` produced correct output (handles, paths, dep counts)
- Zero performance cost: the file is ~3 KB and loads once at startup
- Can switch to binary later if ever needed — the Serialize/Deserialize interface doesn't change

**Magic header:** `JRMA` = **JR**Engine **M**anifest **A**sset. First line of the file. Parser rejects anything that doesn't start with it.

**Format — one asset per line, comma-separated:**

```
JRMA 1
count 52

handle,          assetType,                    filepath,               uniqueID, canLoadAsync, deps, [dep handles...]
a3f2b1c4d5e6f789,Texture2D,                   HUD/Logo_Anim.png,      ,         0,            0
12ab34cd56ef7890,BubbleBobble::AnimsData,      Anims/Logo.txt,         ,         0,            1,    a3f2b1c4d5e6f789
b9c8d7e6f5a4b3c2,Font,                         Fonts/Pixel_NES.otf,   @20,      0,            0
...
```

Rules:
- Line 1: `JRMA <version>`
- Line 2: `count <N>`
- Line 3+: one entry per line — `handle, assetType, filepath, uniqueID, canLoadAsync, depCount [,dep0 ,dep1 ...]`
- `//` lines are comments (skip during parse)
- `uniqueID` may be empty (two adjacent commas)
- Handle values are 16-digit lowercase hex

The manifest for BubbleBobble's ~52 assets will be well under 5 KB.

### 6. Level 2 Scene Files (.scene)

**Problem:** Asset references and entity placement data are hardcoded in C++ builders. There is no data file that describes "what a scene needs and what it contains." This makes it impossible to add new levels or tweak layouts without recompiling.

**Solution:** Each scene gets a `.scene` file under `Data/Scenes/`. A `SceneDescriptor` asset type loads this file. The `.scene` file is the canonical description of a scene's asset wiring and entity placement. Builders become **scene interpreters** — they read from a `SceneDescriptor` instead of constructing everything from hardcoded paths.

This is **Level 2 scene serialization**: data-driven placement and asset routing, with component wiring still handled in code. Full component serialization (Level 3) is deferred until there is an editor.

**What goes in a `.scene` file:**
- Named asset references (virtual paths → resolved to handles at load time)
- Entity placement data: type + position + any per-instance config

**What stays in code:**
- Component wiring (how a ZenChan is assembled, FSM setup, input binding)
- Scene graph construction (which GameObjects get which components)
- Any logic that is not configuration

**File format — simple CSV-style text, consistent with existing `.txt` data files:**

```
// Key-value asset references
// Format: key,virtualPath
tilemap,Levels/1/TileMapData.txt
leveldata,Levels/1/LevelData.txt

// Entity placement
// Format: entity,type,x,y[,extraParam]
entity,ZenChan,120,200
entity,ZenChan,300,150
entity,Player,238,450,0
```

The `SceneDescriptor` asset stores:
- `std::map<std::string, AssetHandle> assets` — named handles (e.g. `"tilemap"`, `"font_20"`)
- `std::vector<EntitySpec> entities` — placement list (type string, position, optional params)

The importer populates `dependencies` from all referenced asset handles, so `RuntimeRM` pre-loads everything before the builder runs.

**How builders change:**

```cpp
// Before — hardcoded path
LevelBuilder(levelScene, "Levels/1").Build();

// After — reads from SceneDescriptor
auto desc = ResourceManager::GetAsset<SceneDescriptor>(GetRegisteredHandle("Scenes/Level1.scene"));
LevelBuilder(levelScene, *desc).Build();

// Inside LevelBuilder — asset lookup by key instead of hardcoded path
auto tileMap = ResourceManager::GetAsset<TileMap>(desc.GetAssetHandle("tilemap"));
auto levelData = ResourceManager::GetAsset<LevelData>(desc.GetAssetHandle("leveldata"));
```

**Relationship to the AssetManifest:** All `.scene` files are registered in `AssetManifest::RegisterAll()` just like any other asset. Their dependencies are auto-declared by the `SceneDescriptorImporter` (since it can read the file and resolve paths to handles at registration time). This is the one case where auto-detection of dependencies is practical — the importer parses the file to find all virtual paths, resolves them to handles, and declares them as dependencies.

**Relationship to LevelData.txt:** LevelData.txt already handles enemy/player spawn positions. The `.scene` file for a level is a thin wrapper that names the `TileMapData.txt` and `LevelData.txt` assets. As the game grows, more per-level config (music, background color, special rules) can be added to the `.scene` file without touching code.

### 7. Always Regenerate Manifest at Startup

The manifest is written every run by the editor phase and immediately read by the RuntimeResourceManager. This is simpler than checking if it exists (and dealing with stale manifests when assets change).

In a real engine you'd only regenerate when assets change (build step). That requires change detection — overkill for this project.

### 7. RuntimeResourceManager: Synchronous + Dependency-Resolving

No worker thread. Synchronous only. `GetAsset(handle)`:

```
1. Cache hit? → return immediately
2. Look up metadata in AssetRegistry
3. For each dep in metadata.dependencies: GetAsset(dep)  ← recursive
4. Load from loose file via AssetImporter
5. Cache and return
```

Cycle detection via a `visited` set passed through the recursion. Throws on circular deps.

This is "as if" assets came from a binary blob where the engine resolves the dependency graph before deserializing — just with actual file I/O instead of offset reads.

## AssetImporter: Two Distinct Overloads

`AssetImporter::ImportAsset` has two completely different overloads. Confusing them is the most likely source of bugs during implementation:

```cpp
// Overload 1 — REGISTRATION (called in RegisterAll())
// Reads metadata from the importer, computes a hash-based handle,
// stores {handle→metadata} in AssetRegistry. No file I/O. Returns the handle.
AssetHandle AssetImporter::ImportAsset(IAssetImporter&& importer);

// Overload 2 — LOADING (called by RuntimeRM::LoadAssetAndDeps)
// Looks up the import function for metadata.assetType, calls it to read
// the actual file from disk, returns a populated AssetRef<Asset>.
AssetRef<Asset> AssetImporter::ImportAsset(AssetHandle handle, const AssetMetadata& metadata);
```

`RegisterAll()` only ever calls overload 1 — it populates the registry with metadata but reads zero files.
`RuntimeRM::LoadAssetAndDeps()` only ever calls overload 2 — it loads files but never touches the registry.

## Startup Flow

```
JREngine::Run(registerAssets, buildScenes)
│
├─ registerAssets():   [EditorResourceManager active]
│    AssetManifest::RegisterAll()
│      → ImportAsset() for every asset → AssetRegistry populated
│    EditorRM::SerializeManifest("Data/asset_manifest.txt")
│    ServiceLocator ← new RuntimeResourceManager("Data/asset_manifest.txt")
│      → Deserialize manifest → AssetRegistry ready
│
└─ buildScenes():   [RuntimeResourceManager active]
     Builders run:
       GetRegisteredHandle("Textures/bub.png") → AssetHandle
       ResourceManager::GetAsset<Texture2D>(handle)
         → RuntimeRM::GetAsset(handle)
           → load deps first → load asset → cache → return
     SceneManager::Start() → game loop
```

## Problems Encountered During Planning

### AnimsData Texture Paths

`AnimDataImporter` reads a CSV/TXT file and stores texture paths as strings inside the `AnimsData` object. These paths are later used in `Utils::CreateAnimationClipFromAnimData()` to load textures. The problem: these texture paths are discovered at runtime (inside the AnimsData data), not known statically.

**Resolution:** Register these textures explicitly in `AssetManifest::RegisterAll()` by enumerating them manually. The list is stable (game assets don't change at runtime). This is consistent with the "explicit manifest" philosophy — in a real engine the editor would have tracked these references automatically, we just do it by hand.

The virtual paths in `data.path` (e.g. `"Player/Bubby/Run_Anim.png"`) must exactly match what's registered in the manifest. Since we store relative paths in metadata, this works directly.

### TileMapImporter Recursive Import

`TileMapImporter::ImportAsset` was calling `AssetImporter::ImportAsset(TextureImporter(filePath))` inside its own import function to load the tile textures it needed. This was fragile and created hidden dependencies.

**Resolution:** In the new model, by the time `TileMapImporter::ImportAsset` runs, all its declared dependencies (the tile textures) have already been loaded by `RuntimeRM::LoadAssetAndDeps()`. The TileMapImporter changes to look up pre-loaded textures from the registry rather than importing them:

```cpp
// Before (recursive import inside import — bad)
auto texHandle = AssetImporter::GetInstance().ImportAsset(TextureImporter(fullTexPath));
auto tex = ResourceManager::GetAsset<Texture2D>(texHandle);

// After (lookup pre-registered handle — clean)
auto texHandle = AssetRegistry::GetInstance().GetHandleAtPath(relTexPath);
auto tex = ResourceManager::GetAsset<Texture2D>(texHandle);  // already in cache
```

### FontImporter Method Chaining

`FontImporter::SetSize()` returns `FontImporter&`. `IAssetImporter::DependsOn()` returns `IAssetImporter&`. These can't be chained cleanly across the base/derived boundary:

```cpp
// Won't compile cleanly:
ai.ImportAsset(FontImporter("font.otf").SetSize(20).DependsOn(x));
//                                                  ^ returns IAssetImporter&, not FontImporter&
```

**Resolution:** Fonts have no dependencies, so `DependsOn()` is never called on font importers in practice. For importers that do use `DependsOn()`, it's called as a separate statement before passing to `ImportAsset()`.

### MSVC /WX: Unused `AssetHandle` Return Values

`AssetImporter::ImportAsset()` returns `AssetHandle`. In `RegisterAll()`, some handles are needed for `DependsOn()` calls (tilemap textures), others aren't. MSVC treats discarded return values of `[[nodiscard]]` functions as warnings → errors.

**Resolution:** Store needed handles in named variables. For handles not used as deps, use `(void)ai.ImportAsset(...)` or `[[maybe_unused]] auto h = ...`. The `ImportAsset` function should be marked `[[nodiscard]]` to catch unintentional discards, but the manifest code intentionally discards some.

### AssetRegistry Re-Population

`RuntimeResourceManager` constructor calls `AssetRegistry::Deserialize()`, but the AssetRegistry singleton was already populated by `AssetManifest::RegisterAll()` (which ran during the editor phase, same process). This means `Deserialize()` tries to register assets that are already there.

**Resolution:** Not actually a problem — `AssetRegistry::RegisterAsset()` already deduplicates by virtual path. If an asset is already registered with the same virtual path, it returns the existing handle. The `Deserialize()` call is effectively a no-op for already-registered assets, and correctly adds any that somehow weren't (shouldn't happen, but safe).

## Verification Plan

1. `asset_manifest.txt` created on startup (check file size > 0, magic bytes)
2. Log handle count deserialized by RuntimeRM — must match `RegisterAll()` registration count
3. `GetRegisteredHandle()` asserts if called for an unregistered asset — drives manifest completeness
4. Run all game states: MainMenu → Level 1 → Level 2 → Level 3 → GameOver → restart
5. Kill and restart: log first 5 handles — must be **identical** across runs (hash stability)
6. Font variants: `@20` and `@30` produce **distinct** handles
7. Tilemap deps: assert texture `GetAsset<Texture2D>()` returns non-null inside `TileMapImporter::ImportAsset` (confirms dep pre-loading)

        ai.ImportAsset(TileMapImporter(base + "TileMapData.txt")
            .DependsOn(bigTex).DependsOn(smallTex));
        ai.ImportAsset(LevelDataImporter(base + "LevelData.txt"));
    }

    // ── SCENE DESCRIPTORS ────────────────────────────────────────────────────
    // Must be LAST — SceneDescriptorImporter::GetMetadata() resolves virtual
    // paths to handles via AssetRegistry::GetHandleAtPath(), which only works
    // after all referenced assets above are already registered.
    ai.ImportAsset(SceneDescriptorImporter("Scenes/MainMenu.scene"));
    ai.ImportAsset(SceneDescriptorImporter("Scenes/LoadingScreen.scene"));
    ai.ImportAsset(SceneDescriptorImporter("Scenes/GameOver.scene"));
    ai.ImportAsset(SceneDescriptorImporter("Scenes/HUD.scene"));
    for (int i = 1; i <= 3; ++i)
        ai.ImportAsset(SceneDescriptorImporter("Scenes/Level" + std::to_string(i) + ".scene"));
}
```

### Notes on the code above

- **Font chaining**: `SetSize()` returns `FontImporter&`, `DependsOn()` returns `IAssetImporter&` — they can't be chained across the boundary. Called as separate statements before `ImportAsset`.
- **Bobby textures**: `Player/Bobby/Bubble_Anim.png`, `Intro_Anim.png`, `Burn_Anim.png` are imported now (referenced by Bubble.txt, Intro_P2.txt, Fail_P2.txt). Bobby gameplay textures (`Idle`, `Run`, `Shoot`, `Death`) are NOT yet registered — add them when P2 gameplay is wired up via `Anims/P2.txt`.
- **AnimsData textures as deps**: The `DependsOn()` declarations here mirror what the txt files reference internally. When `RuntimeRM` loads e.g. `Anims/P1.txt`, it will pre-load all 4 Bubby textures first, so `Utils::CreateAnimationClipFromAnimData()` finds them in cache immediately.
- **Levels loop**: All 3 levels follow the same pattern. If levels are added later, increment the loop bound.
- **MSVC /WX**: All `ImportAsset` return values assigned to named variables are used as `.DependsOn()` args. For assets with no dependents (sounds, music, HUD texture, LevelData), the return value is discarded — use `(void)` or drop the assignment entirely since `[[nodiscard]]` may not be on `ImportAsset`.

```cpp
void AssetRegistry::Serialize(std::ostream& out) const
{
    out << "JRMA 1\n";
    out << "count " << m_AssetHandleToMetadata.size() << "\n\n";

    for (auto& [handle, meta] : m_AssetHandleToMetadata)
    {
        // handle, assetType, filepath, uniqueID, canLoadAsync, depCount [,dep0, dep1, ...]
        out << std::hex << std::setw(16) << std::setfill('0')
            << static_cast<uint64_t>(handle) << std::dec;
        out << ',' << meta.assetType;
        out << ',' << meta.filepath.generic_string();
        out << ',' << meta.uniqueID;
        out << ',' << (meta.canLoadAsync ? 1 : 0);
        out << ',' << meta.dependencies.size();
        for (AssetHandle dep : meta.dependencies)
            out << ',' << std::hex << std::setw(16) << std::setfill('0')
                << static_cast<uint64_t>(dep) << std::dec;
        out << '\n';
    }
}

bool AssetRegistry::Deserialize(std::istream& in)
{
    std::string header;
    if (!std::getline(in, header) || header != "JRMA 1")
        return false;

    std::string countLine;
    if (!std::getline(in, countLine) || countLine.rfind("count ", 0) != 0)
        return false;
    // (count is informational — we just read until EOF)

    std::string line;
    while (std::getline(in, line))
    {
        if (line.empty() || line[0] == '/') continue;

        // Split by comma
        std::vector<std::string> tok;
        std::stringstream ss(line);
        std::string t;
        while (std::getline(ss, t, ',')) tok.push_back(t);
        if (tok.size() < 6) continue;

        AssetHandle handle{ std::stoull(tok[0], nullptr, 16) };
        AssetMetadata meta;
        meta.assetType    = tok[1];
        meta.filepath     = tok[2];
        meta.uniqueID     = tok[3];
        meta.canLoadAsync = tok[4] == "1";
        uint32_t depCount = static_cast<uint32_t>(std::stoul(tok[5]));
        for (uint32_t d = 0; d < depCount; ++d)
            meta.dependencies.emplace_back(std::stoull(tok[6 + d], nullptr, 16));

        std::string vPath = meta.GetVirtualPath();
        m_AssetHandleToMetadata.emplace(handle, meta);
        m_PathToAssetHandle.emplace(vPath, handle);
    }
    return in.eof() || in.good();
}
```

Include `<iomanip>` and `<sstream>` for the hex formatting and line splitting.

#include "JREngine/Core/UUID.h"

#include <stdexcept>

{
    RuntimeResourceManager::RuntimeResourceManager(const std::filesystem::path& manifestPath)
    {
        std::ifstream in(manifestPath, std::ios::binary);
        if (!in)
            throw std::runtime_error("RuntimeResourceManager: asset_manifest.txt not found");
        if (!AssetRegistry::GetInstance().Deserialize(in))
            throw std::runtime_error("RuntimeResourceManager: failed to parse asset_manifest.txt");
    }

    bool RuntimeResourceManager::IsValidAssetHandle(AssetHandle handle) const
    {
        return AssetRegistry::GetInstance().IsValidAssetHandle(handle);
    }

    bool RuntimeResourceManager::IsAssetLoaded(AssetHandle handle) const
    {

    }

    AssetRef<Asset> RuntimeResourceManager::GetAsset(AssetHandle handle, AssetLoadMode /*mode*/)
    {
        auto it = m_LoadedAssets.find(handle);
        if (it != m_LoadedAssets.end())
            return it->second;

        if (!AssetRegistry::GetInstance().IsValidAssetHandle(handle))
            return nullptr;

        std::unordered_set<uint64_t> visited;
        return LoadAssetAndDeps(handle, visited);
    }

    AssetRef<Asset> RuntimeResourceManager::LoadAssetAndDeps(AssetHandle handle,
                                                              std::unordered_set<uint64_t>& visited)
    {
        if (!visited.insert(static_cast<uint64_t>(handle)).second)
            throw std::runtime_error("RuntimeResourceManager: circular asset dependency detected");

        // Already loaded by a previous dep path
        auto it = m_LoadedAssets.find(handle);
        if (it != m_LoadedAssets.end())
        {
            visited.erase(static_cast<uint64_t>(handle));
            return it->second;
        }

        const AssetMetadata& meta = AssetRegistry::GetInstance().GetMetadata(handle);

        // Load dependencies depth-first before this asset
        for (AssetHandle dep : meta.dependencies)
            LoadAssetAndDeps(dep, visited);

        AssetRef<Asset> asset = AssetImporter::GetInstance().ImportAsset(handle, meta);
        if (asset)
        {
            asset->SetHandle(handle);
            m_LoadedAssets.emplace(handle, asset);
        }

        visited.erase(static_cast<uint64_t>(handle));
        return asset;
    }

    AssetHandle RuntimeResourceManager::AddAsset(AssetRef<Asset> asset)
    {
        AssetHandle handle = UUID::Generate();
        asset->SetHandle(handle);
        m_LoadedAssets.emplace(handle, asset);
        return handle;
    }
}

**`SceneDescriptorImporter.cpp` — key logic:**

The importer parses the `.scene` file twice:
1. In `GetMetadata()` — resolve virtual paths to handles and declare them as `dependencies`
2. In `ImportAsset()` — parse again, build the `assets` map and `entities` list

```cpp
AssetMetadata SceneDescriptorImporter::GetMetadata() const
{
    // Parse file to extract all virtual paths, resolve to handles for dep declaration
    AssetMetadata meta;
    meta.assetType = SceneDescriptor::GetStaticType().data();
    meta.filepath = m_Path;  // relative path to .scene file

    std::ifstream f(AssetImporter::GetInstance().GetFullDatapath(m_Path));
    std::string line;
    while (std::getline(f, line))
    {
        if (line.empty() || line[0] == '/' || line[0] == '#') continue;
        if (line.rfind("entity,", 0) == 0) continue;  // skip entity lines

        // key,virtualPath
        auto comma = line.find(',');
        if (comma == std::string::npos) continue;
        std::string vPath = line.substr(comma + 1);

        AssetHandle dep = AssetRegistry::GetInstance().GetHandleAtPath(vPath);
        if (dep.IsValid())
            meta.dependencies.push_back(dep);
    }
    return meta;
}

AssetRef<Asset> SceneDescriptorImporter::ImportAsset(AssetHandle, const AssetMetadata& metadata)
{
    auto desc = CreateAssetRef<SceneDescriptor>();
    auto fullPath = AssetImporter::GetInstance().GetFullDatapath(metadata.filepath);
    std::ifstream f(fullPath);
    std::string line;

    while (std::getline(f, line))
    {
        if (line.empty() || line[0] == '/' || line[0] == '#') continue;

        auto tokens = Split(line, ',');  // simple helper: split by comma
        if (tokens[0] == "entity")
        {
            // entity,type,x,y[,param]
            EntitySpec spec;
            spec.type = tokens[1];
            spec.x = std::stof(tokens[2]);
            spec.y = std::stof(tokens[3]);
            if (tokens.size() > 4) spec.param = tokens[4];
            desc->entities.push_back(spec);
        }
        else
        {
            // key,virtualPath → resolve to handle (already loaded as dep)
            std::string key = tokens[0];
            std::string vPath = tokens[1];
            AssetHandle h = AssetRegistry::GetInstance().GetHandleAtPath(vPath);
            desc->assets.emplace(key, h);
        }
    }
    return desc;
}
```

### Pitfalls checklist

- **MSVC /WX — unused handles in RegisterAll()**: `ImportAsset` return values not used as deps must be suppressed. Pattern: `(void)ai.ImportAsset(...)` for assets with no dependents.
- **Font chaining**: `SetSize()` returns `FontImporter&`, `DependsOn()` returns `IAssetImporter&`. Can't chain across the boundary. Call `SetSize()` first, then pass to `ImportAsset()` as separate statements (fonts have no deps so `DependsOn` is never needed on fonts anyway).
- **Virtual path normalization**: Always use `generic_string()` (forward slashes) as the hash input. Never `native()` or `string()` on Windows.
- **TileMap path reconstruction**: After the relative-path fix, `metadata.filepath` is `"Levels/1/TileMapData.txt"`. Use `metadata.filepath.parent_path()` to get `"Levels/1"` for building relative texture lookup paths.
- **AssetRegistry re-population**: `Deserialize()` is called on an already-populated registry (EditorRM phase already ran). This is safe — `RegisterAsset` deduplicates by virtual path. No double entries.
- **`AddAsset()` in RuntimeRM**: Still needed for runtime-created assets (e.g. Sprites from `SpriteEditor::SplitTexture2D`). Uses `UUID::Generate()` (session-unique, high-bit sentinel), not `FromPath()`.
- **Scene files registered last in RegisterAll()**: `SceneDescriptorImporter::GetMetadata()` calls `AssetRegistry::GetHandleAtPath()` to resolve dep paths — this only works if all referenced assets are already registered. Always register `.scene` files after all other assets.
- **SceneDescriptor deps are auto-detected** (the one exception to the "explicit deps" rule): the importer must parse the file to find the paths. This is acceptable here because the file is small, the parsing is trivial, and it would be impractical to redeclare all scene deps in `RegisterAll()` manually.
